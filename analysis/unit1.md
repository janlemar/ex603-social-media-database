### Modeling Justification
For this project, I chose to model a social media platform using five relations: users, posts, likes, hashtags, and post_hashtags. Each of these relations have a different purpose and role. Users would represent the people that use the social media platform, posts would represent the content that is being produced/created, likes represent the interaction between the post and the users themselves, hashtags represent the categories, and post_hashtags connect the posts to hashtags.

For the primary keys, I wanted to use integer IDs for users, posts, and hashtags. The sole reason is to make a unique identifier that cannot change. A lot of the times in social media, people change their usernames, display names, or hashtags and I wanted to use something that cannot be modified. For likes, I used a composite primary key of user_id and post_id. This is because a user should not be able to like the same post more than once. I used the same idea for post_hashtages, where post_id and hashtag_id together make the primary key. The same idea also lies in this, as this prevents the same hashtag being associated to the same post more than once. 

The foreign keys are also important for keeping the relationships between the tables valid. The user_id and post_id in likes reference the existing users and posts. The post_id and the hashtag_id in post_hashtags references existing posts and hashtags. I chose On Delete Cascade for all four foreign keys because the related records do not have a purpose once they've been deleted from their connections. For example, if a user is deleted their likes should be removed. If a post is deleted, its like and hashtag connections (not the hashtag itself) should also be removed. If a hashtag is deleted, the connections to posts should be removed (but the post itself should stay). 

Beyond primary and foreign keys, I chose to set certain rules directly in the schema rather than relying on the application to catch them. The composite primary keys on likes and post_hashtags are one of the examples for this regulation. Instead of depending on the application to check if the user has already liked the post, I enforced this early on to prevent any duplicate likes from happening. I'd also use certain restrictions that prevents anyone from going off-scope like using negative values, any incorrect symbols/characters. I'd prefer leaving certain rules to the application itself like content moderation, any posting guidelines, and aspects that are more behavioral. These can be left to the application, as they can change over time and don't threaten any of the data itself.

### Reflection

One decision that I think a different designer could disagree with is my use of composite primary keys. They can argue that instead of my method, they can put a unique constraint on the pair. My way of thinking was using that it would only track whether that user currently likes a post, not the full history of every single like. Since the primary key can't repeat, if a user unlikes a post and then likes it again after, the row just gets deleted and reinserted, and there's no record of it every happening more than once. 

I went after this method because I don't think that it's necessary to keep a record of every single time a user has liked a post. Its main purpose is to show which users are currently liking these specific posts. Likes would also have a lot of read and write activity since there are many users in social media that constantly like and unlike posts. For a fast, high-volume read and write pattern, this is the right call. I think its history would only matter if one needed to analyze engagements in a post.
